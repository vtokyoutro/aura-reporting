# AURA v0.7.1. Хранение аватарок

Серверная часть подготовлена для ревью. Рабочие Supabase Storage, схема, Auth и RLS не проверялись и не менялись. [Проект SQL](avatar-storage-review.sql) находится вне каталога автоматических миграций. Клиентская настройка `VITE_AVATAR_STORAGE_ENABLED` отключена по умолчанию.

## Исходные данные

AURA загружает `staff.id`, `display_name` и `role` по ID пользователя Supabase Auth. Интерфейс считает руководителем пользователя с `staff.role = 'leader'`. Запрос списка сотрудников для руководителя сам по себе не показывает, какие сотрудники входят в его команду или какие права проверяет сервер. В репозитории нет определения таблицы `staff`, действующих политик RLS и конфигурации Storage. Доступность Storage и наличие одноимённого bucket нужно подтвердить на согласованном окружении. [Загрузка профиля](../src/renderer/src/App.tsx) · [Запрос списка сотрудников](../src/renderer/src/lib/report-data.ts)

## Права и контракт

| Кто | Чтение | Создание, замена и удаление |
| --- | --- | --- |
| Чаттер | Свой аватар | Свой аватар |
| Руководитель | Свой аватар | Свой аватар |
| Посетитель без входа или анонимная сессия Supabase Auth | Запрещено | Запрещено |

Доступ к единственному пути `<auth.uid()>/avatar.webp` определяется подписанным токеном, точным путём и `storage.objects.owner_id`. Политики применяются к постоянным аккаунтам Supabase Auth, включая собственный объект постоянного аккаунта без строки `staff`. В интерфейсе AURA настройки профиля доступны после загрузки `staff`. Клиент по умолчанию показывает инициалы остальных сотрудников. [Владелец объекта](https://supabase.com/docs/guides/storage/security/ownership) · [Анонимные сессии](https://supabase.com/docs/guides/auth/auth-anonymous)

Клиент загружает WebP по HTTPS с токеном текущего аккаунта. Он сохраняет изображение через `POST` с `x-upsert: true`, читает через GET с авторизацией и удаляет через `DELETE` с единственным точным путём в `prefixes`. Обновление использует RLS-права `INSERT`, `SELECT` и `UPDATE`. SQL проверяет существующую и новую строку при обновлении, а также ограничивает маршруты этими операциями. Создание подписанных ссылок, размещение в других папках, выдача списков и перемещение объектов под этим правилом запрещены. Ограничивающая политика применяется вместе с уже существующими разрешающими политиками и не ограничивает другие bucket. [Доступ к файлам](https://supabase.com/docs/guides/storage/security/access-control) · [Операции Storage](https://supabase.com/docs/guides/storage/schema/helper-functions) · [Сочетание политик PostgreSQL](https://www.postgresql.org/docs/current/sql-createpolicy.html)

## Порядок после согласования

1. В согласованном тестовом окружении проверить, что `staff-avatars` ещё не существует. Просмотреть RLS на `storage.objects` и `storage.buckets`, права клиентских ролей и доступ к Storage. Клиентские `anon` и `authenticated` не должны иметь возможности создать одноимённый bucket или изменить его параметры. Проверить, что постоянные тестовые аккаунты получают подписанный JWT со значением `is_anonymous: false`. Для сверки политик и доступности вспомогательной функции можно использовать запросы в конце этого раздела.
2. Установить [политики](avatar-storage-review.sql) до создания bucket. Это исключает промежуток, в котором существующие разрешающие политики могли бы открыть новый bucket. Скрипт завершается ошибкой, если имя уже занято, RLS отключён или в этой версии Storage нет необходимой вспомогательной функции. Существующий одноимённый bucket требует отдельного ревью.
3. Создать **стандартный приватный** bucket `staff-avatars` через Storage Dashboard или API администратора. Для точной настройки через административный SDK передать `public: false`, `fileSizeLimit: 524288`, `allowedMimeTypes: ['image/webp']`. Оставить версионирование отключённым, если оно доступно. SQL меняет только политики. Операции с файлами выполняются через Storage API, чтобы метаданные и сами файлы оставались согласованными. [Создание bucket](https://supabase.com/docs/guides/storage/buckets/creating-buckets) · [Ограничения загрузки](https://supabase.com/docs/guides/storage/uploads/file-limits) · [Схема Storage](https://supabase.com/docs/guides/storage/schema/design)
4. Сверить конфигурацию нового bucket и выполнить сценарии ниже с обычными тестовыми аккаунтами. После отдельного решения о включении функции собрать клиент с `VITE_AVATAR_STORAGE_ENABLED=true` для окружения, где прошла серверная проверка.

```sql
select schemaname, tablename, policyname, permissive, roles, cmd, qual, with_check
from pg_policies
where schemaname = 'storage' and tablename in ('buckets', 'objects')
order by tablename, policyname;

select to_regprocedure('storage.allow_any_operation(text[])');

select id, name, public, file_size_limit, allowed_mime_types,
       to_jsonb(bucket) ->> 'versioning_status' as versioning_status
from storage.buckets as bucket
where id = 'staff-avatars' or name = 'staff-avatars';
```

## Серверная приёмка

- С постоянными тестовыми аккаунтами чаттера и руководителя проверить первый `POST`, замену, чтение после входа на втором устройстве и удаление. Для каждой операции повторить запрос с другим UID в пути. Убедиться, что объект второго пользователя сохранил исходные байты. Пустой ответ операции удаления сам по себе не доказывает отказ.
- Проверить запрос без JWT, без входа с publishable key и с анонимным JWT, если анонимный вход уже доступен в тестовом окружении. Проверить публичный URL, создание подписанной ссылки, получение списка, другой файл в своей папке и вложенную папку.
- Проверить отказ для загрузки WebP свыше 524 288 байт и объявленного MIME-типа, отличного от `image/webp`. MIME-ограничение Storage и проверка реального содержимого в клиенте выполняют разные задачи. Если понадобится гарантировать формат байтов и размер в пикселях даже при прямых вызовах API, потребуется отдельно согласованный серверный декодер.
- Проверить смену аккаунта при загрузке, очистку предпросмотра и отображаемого аватара при выходе, а также отсутствие запросов к аватаркам чужих сотрудников. Клиент читает файл без кеша, проверяет сигнатуру и выводит WebP через `data:image/webp` в памяти сессии. CSP не расширяется. Серверный токен может действовать до истечения срока, поэтому проверка выхода из интерфейса не заменяет проверку RLS с токеном другого пользователя. [Кеширование приватных объектов](https://supabase.com/kb/troubleshooting/storage-private-bucket-files-still-accessible-after-remove-access-or-logout)
- Проверить, что старые bucket работают с прежними правилами. Если функцию нужно отключить, сначала отключить клиентский флаг. Удаление самого bucket или объектов проводится через Storage после отдельного согласования. Пока bucket существует, его ограничивающую политику следует сохранить.

## Отдельное расширение для руководителей

После подтверждения серверной связи между руководителем и конкретным сотрудником можно добавить чтение аватаров своей команды. Доступ проверяется по защищённому источнику ролей и членства под UID запрашивающего и UID владельца объекта. Роль `leader` без подтверждённой связи с конкретным сотрудником недостаточна. Доступ используется только для авторизованного GET канонического файла. Для такой версии действующее ограничение `FOR ALL` заменяется в одной транзакции правилами по операциям. Правила `INSERT`, `UPDATE` и `DELETE` продолжают проверять владельца и точный путь даже при наличии других разрешающих политик. Тесты должны отдельно подтвердить чтение члена своей команды, отказ вне команды и невозможность редактирования любого чужого аватара.
